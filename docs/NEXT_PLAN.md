# ConnectX 冲分方案

## 文档定位

这份文档只服务一个目标：

- 在 Kaggle ConnectX 上拿更多分

它不是一份“工程规范”文档，也不是一份“优雅重构”文档，更不是一份“研究探索路线图”。

判断标准只有一个：

- 这件事能不能让最终提交到 Kaggle 的 `submission.py` 更强

如果能，就做。
如果不能，就先不做。


## 核心原则

这个项目里真正会影响排行榜分数的，只有一个产物：

- 最终提交到 Kaggle 的、合法可运行的、单文件 `submission.py`

其他一切内容都只是辅助：

- 文档本身不加分
- 测试本身不加分
- 代码结构本身不加分
- 训练脚本本身不加分
- 本地框架本身不加分

它们只有在能帮助我们更快产出更强的 `submission.py` 时，才有价值。


## 我们真正优化的东西

所有决策都按下面这个优先级排序：

1. 是否提高 Kaggle 实战胜率
2. 是否加快更强版本的迭代速度
3. 是否降低浪费提交次数的风险
4. 最后才考虑代码是否优雅、是否通用、是否好维护


## 对当前仓库的冲分视角判断

这个仓库已经不是一个玩具项目了，已经具备了比较强的基础：

- Bitboard
- NegaScout
- 置换表
- Killer Heuristic
- 基本开局库
- 本地评估与训练框架

所以冲分路线不应该是“推倒重来”，而应该是沿着当前搜索型 Agent 继续往上打。

从冲分角度看，当前最值得盯的几个问题是：

1. `submission.py` 可能没有把 2 秒预算真正吃满。
2. 开局库偏浅。
3. 训练和调参结果没有稳定地落进最终提交文件。
4. 部分训练代码本身不够可靠，容易浪费实验时间。


## 当前最值钱的问题

### 1. 搜索时间用得太保守

当前 `submission.py` 的总预算是 `1900ms`，但搜索停止条件非常保守。

相关位置：

- `submission.py:34`
- `submission.py:634`
- `submission.py:660-663`

冲分视角下，这个问题很要命，因为：

1. 你已经有一套不错的搜索器了。
2. 多吃一点时间，往往就能多搜 1 层甚至 2 层。
3. ConnectX 这类游戏对搜索深度非常敏感。

换句话说，这不是“性能优化”，这是直接的战斗力优化。


### 2. 开局知识太少

当前开局库是有的，但覆盖面还不够。

相关位置：

- `submission.py:588`
- `submission.py:735-737`

冲分视角下，开局库的重要性很高，因为：

1. 每一局都会进入开局。
2. 开局走差了，后面搜索是在劣势局面上补救。
3. Connect Four 是已解游戏，开局理论是可以直接利用的。

如果只看“投入产出比”，补开局库通常比继续微调普通评估函数更划算。


### 3. 训练结果不一定真正进了最终提交版

这是当前仓库里最危险的问题之一。

从代码看，存在几条明显断链：

1. `evaluate/optimize.py` 会在运行时 monkey-patch `submission.py`，同时把结果写到 `agents/weights.py`
2. 但 `submission.py` 本身不会自然读取 `agents/weights.py`
3. `evaluate/td_learn.py` 写的是 `sub.HMAP_POS`
4. 但 `submission.py` 实际使用的是 `_HMAP_POS`
5. `submission.py` 里 `_TD_WEIGHTS` 默认是 `None`

这意味着：

- 你可能本地做了很多调参和训练
- 但这些结果不一定真的体现在最终交上 Kaggle 的文件里

冲分视角下，这种问题必须排第一批解决，因为它会让后面的努力大量折损。


### 4. 训练脚本本身有稳定性风险

`evaluate/td_learn.py` 里直接使用了 `_COL0_MASK`、`_COL6_MASK` 之类的常量，但文件里没有看到完整同源定义。

相关位置：

- `evaluate/td_learn.py:67-70`

冲分视角下，这类问题的含义不是“代码不优雅”，而是：

- 训练结果可能不可信
- 训练脚本可能中途炸掉
- 时间会浪费在修训练环境，而不是提升提交强度


## 冲分路线总纲

如果完全只为分数服务，那么后续路线应该是：

1. 先修“实验结果到最终提交物”的链路
2. 再把当前搜索器的时间利用率和效率做上去
3. 再加强开局和终局的确定性能力
4. 最后才继续扩大训练和学习型优化的投入

简化成一句话就是：

- 先把现有强搜索器榨干，再谈更复杂的学习路线


## 第一阶段：先修最终提交链路

### 目标

确保所有真正有效的调参和训练结果，最后都能稳定地进入 Kaggle 提交文件。

### 为什么这是第一位

因为如果这件事不解决，后面很多实验即使有效，也无法转化成榜单分数。

### 应该做到的状态

必须形成一条稳定链路：

1. 本地训练或调参得到最优参数
2. 把这些参数写进最终提交版 `submission.py`
3. 用这个最终文件做本地对战验证
4. 提交这个最终文件

### 冲分导向的做法

不要让“最优参数”只存在于以下位置：

- 脚本运行时的临时 monkey-patch
- `agents/weights.py`
- `agents/td_weights.py`
- 某次训练日志里
- 某个注释说明里

最优参数必须落到最终提交物里。

### 具体建议

做一个专门的“构建提交版”脚本，作用只有一个：

- 把当前最优常量、开局库、可选 learned 参数全部压进一个最终 `submission.py`

这样一来，训练代码和比赛提交版可以继续分开，但最终实力不会丢失。


## 第二阶段：把时间预算吃满

### 目标

用同样的 2 秒上限，换来更多有效搜索深度。

### 为什么优先级这么高

因为这是最直接的战斗力来源之一，而且不需要换算法体系。

### 当前问题

现在的停止条件本质上更像：

- “早点停，确保不超时”

而不是：

- “尽量在不超时的前提下把预算吃干净”

### 应该怎么改

把固定阈值改成动态预算模型：

1. 记录当前深度耗时
2. 估算下一深度耗时
3. 预留小安全缓冲
4. 只要还能安全完成下一层，就继续搜

### 建议策略

可以使用：

- 固定安全缓冲 80ms 到 120ms
- 最近两层增长比例估算下一层成本
- 配合 `remainingOverageTime` 动态调节冒险程度

### 预期收益

1. 中残局更强
2. 战术漏看减少
3. 当前引擎不改框架就能涨一截强度


## 第三阶段：先提升搜索效率，再微调评估函数

### 目标

让每一毫秒搜索出更多有效信息。

### 为什么这比继续调权重更重要

一个强搜索器会放大评估函数的价值。
一个弱搜索器会浪费评估函数的价值。

### 优先做的几个东西

1. Aspiration windows
2. Principal variation reuse
3. History heuristic
4. Counter-move heuristic
5. 左右镜像归一化的 TT key

### 为什么镜像归一化很值钱

ConnectX 左右对称性很强。
如果镜像局面占两份 TT 空间，就等于白白浪费内存和命中率。

在固定 2 秒预算下，这种浪费会直接变成分数损失。

### 更好的着法排序优先级

推荐排序优先级：

1. 立即获胜着
2. 强制防守着
3. TT best move
4. Killer move
5. History best move
6. 中心优先的其他着法

这类优化比单纯再改一点评分常量更有可能带来稳定提分。


## 第四阶段：强化开局

### 目标

减少前几步就吃亏的情况，让搜索更频繁地从好局面开始。

### 为什么开局投入回报高

1. 每一局都会进开局
2. 强对手对开局偏差的惩罚很大
3. 开局如果处理好，会直接减轻中盘搜索负担

### 冲分做法

不要为了“代码简洁”把开局库做得太保守。
应当优先做：

1. 补中心开局理论分支
2. 补常见反击路线
3. 补镜像分支
4. 离线生成后压缩进单文件提交版

只要能提升实战，哪怕开局库写得不漂亮，也是值得的。


## 第五阶段：增强终局精确能力

### 目标

在终局尽量少靠启发式猜，多靠精确胜负判断。

### 为什么这一步很关键

很多高质量对局最后拼的不是“谁评估更顺眼”，而是：

- 谁能先算出强制胜
- 谁能先识别必和
- 谁能避免把可和局面下输

### 冲分导向的实现方向

不需要一开始就做完整全局求解器。
更现实的路线是：

1. 当空位少于某阈值时，切换到更精确的终局搜索模式
2. 在终局降低软启发式的影响
3. 强化 forced move、double threat、parity 识别

### 特别值得显式做的终局特征

1. 双威胁
2. 垂直威胁
3. 奇偶威胁转换
4. 强制应手链

这一块是把“强搜索器”推向“真正高分提交版”的分水岭之一。


## 第六阶段：训练只做“放大器”，不做主角

### 目标

让学习型方法为搜索器服务，而不是试图替代搜索器。

### 冲分原则

如果一个 learned 组件不能在最终提交版里稳定提高胜率，那它就不够好。

### 训练更适合承担的角色

1. 调 leaf evaluator 权重
2. 调 move ordering prior
3. 调根节点 tie-break

### 不值得优先做的事情

不要把大量时间花在下面这种方向上：

1. 对 `random` 胜率很好看
2. 本地训练曲线很好看
3. 但最终 `submission.py` 实战没有变强

这类东西对冲分没有意义。


## 评测策略必须升级

如果目标只是分数，那么“怎么比”本身也很重要。

### 不要主要对 `random` 调参

`random` 的用途应该只剩：

1. 检查有没有严重退化
2. 检查有没有明显非法动作或超时问题

真正调参和版本晋升，应该主要对：

1. 当前最强提交版
2. 前几个历史强版本
3. `negamax`
4. 不同风格的内部变体

### 建立 Champion / Challenger 制度

建议一直维持两个角色：

1. Champion：当前最强、最可信的本地版本
2. Challenger：新实验版本

任何新版本都必须先打过 Champion，才有资格考虑提交。

### 建议三段式筛选

1. 快速筛选：20 局
2. 中等确认：100 局
3. 提交前验证：200 局或更多

这样能减少把“偶然赢了几局”的版本误判成强版本。


## 冲分型实验方法

### 好实验

一次只改一个主要因素。

例如：

1. 只改时间管理
2. 只加镜像 TT
3. 只补开局库
4. 只加终局切换

### 坏实验

一次改很多东西，然后赢了也不知道到底是哪一个起作用。

例如：

1. 同时改评估函数、搜索时间、TT 和开局库
2. 同时改训练逻辑和最终提交逻辑
3. 同时改 move ordering 和 root tie-break

冲分项目最怕这种“赢了但不可复现”的实验。


## 最少必须跟踪的指标

如果只为冲分，就只跟踪与分数强相关的指标。

### 引擎指标

1. 平均完成深度
2. 最大完成深度
3. 节点访问数
4. TT hit rate
5. cutoff rate
6. 超时次数

### 对战指标

1. 对 Champion 的胜率
2. 对强对手池的综合胜率
3. 先手和后手分开统计
4. 关键战术局面的失误率

### 提交指标

1. 当前构建出的提交文件版本号
2. 该文件实际内联了哪些常量
3. 提交前验证结果

除了这些，其他指标都属于“可选项”。


## 一周冲分计划

如果现在就要尽快涨分，我建议这样排：

### 第 1 天

1. 修训练与调参结果写入最终提交物的链路
2. 修 TD 注入接口不匹配的问题
3. 确认最优参数真的进了最终 `submission.py`

### 第 2 天

1. 把固定搜索停止阈值改成动态预算
2. 在代表性局面集上做 benchmark
3. 和当前 Champion 对打

### 第 3 天

1. 加 aspiration windows
2. 加 PV reuse
3. 再跑 Champion / Challenger

### 第 4 天

1. 加 TT 镜像归一化
2. 检查镜像回映射正确性
3. 跑中规模对战

### 第 5 天

1. 补开局库
2. 优先补最常见中心线
3. 再打当前 Champion 和 `negamax`

### 第 6 到 7 天

1. 加终局精确模式切换
2. 加显式双威胁识别
3. 选出当前最强提交版准备提交


## 两周冲分计划

如果第一周有效，第二周重点放在：

1. 建更强的对手池
2. 细化终局模式
3. 在搜索器稳定后再调 learned evaluator
4. 严格按 Champion / Challenger 节奏提交


## 这个项目里暂时不该优先做的事

如果只为分数，下面这些都不该排在前面：

1. 大规模重构仓库
2. 把训练框架打磨得特别漂亮
3. 以 MCTS 作为新的主线方向
4. 做复杂报告系统
5. 写很多和冲分无关的文档
6. 为了代码优雅而放弃更强的提交实现


## 我认为最值钱的改动顺序

如果按“投入产出比”来排，我的顺序是：

1. 修最终提交版构建链路
2. 把时间预算吃满
3. 提高着法排序和 TT 效率
4. 扩展开局库
5. 加终局精确求解能力
6. 再继续加大学习型优化投入


## 最终结论

这个项目想继续往上冲分，最现实的路线不是推翻当前搜索器，而是把它做得更像一个真正的高分 Connect Four 提交版：

1. 让一切实验结果都真正进入最终提交物
2. 让现有搜索器把 2 秒预算吃干净
3. 让 TT、排序、开局、终局都更强
4. 让新版本只在打赢旧冠军后才晋升

一句话概括：

- 先把当前这套搜索体系榨干，再谈更花哨的方向

这才是最符合“唯一目的就是拿更多分”的路线。
